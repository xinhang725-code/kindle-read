# 微信读书：插件、独立版与新软件的对照

日期：2026-10-28。用户提供了两份 Google Drive 文件，说明已有不依赖 KOReader 的 Kindle 微信读书软件，并要求与 MiuRead、安卓版对标后补齐缺失功能。

**当前未读取到这两个文件，不能判断其版本、作者、架构或功能缺失。** 两次访问均在云代理 CONNECT 阶段返回 403；这是环境出站策略阻塞，不证明 Drive 文件权限或软件本身有问题。Drive 预览与下载域名已添加到环境草稿，待保存/发布生效。现有 alpha 保留为可复用基础；取得新包后先评估已有实现，不默认继续重复开发同一套功能。

## 为什么 MiuRead 依赖 KOReader

MiuRead 是按 KOReader 插件接口编写的。固定上游提交 `581f9b660097aa42fe33170098346862cf0a9bbf` 的 `main.lua` 直接加载 `ui/uimanager`、`device`、`libs/libkoreader-lfs`；`reader_toolbar.lua` 使用 `ffi/blitbuffer`、`InputContainer`、`Device.screen` 和 UIManager 的刷新/事件机制。安装说明也明确要求放进 `miuread.koplugin` 并重启 KOReader。

它实现微信读书的账号、书架、内容访问、下载、同步等业务，同时使用 KOReader 的文档阅读、排版、输入、窗口、设备适配等能力。因此复制插件或改一个启动脚本无法去掉依赖；独立化需要替换这些实际调用。微信读书服务本身并不要求客户端使用 KOReader，这个依赖来自 MiuRead 当前的实现方式。

**原生书架入口和底层依赖是两件事。** 入口可以直接启动独立应用，也可以启动一个宿主及其插件；两者外观都可能做到少操作，但后一种仍有 KOReader 依赖。用户此前明确要求无 KOReader，在没有改变该要求前，后者只能作为比较对象。

| 方面 | MiuRead + KOReader | 不依赖 KOReader 的独立版 |
| --- | --- | --- |
| 阅读器基础 | 使用已有排版、文档和设备能力 | 自行实现，或使用固件/其他独立引擎 |
| 功能推进 | 更容易复用现有 MiuRead 功能和宿主生态 | 若已有成熟独立版可扩展它；从零重做成本较高 |
| 原生入口体验 | 可研究入口直达，但底层仍需宿主 | 可直接控制应用入口和生命周期 |
| 升级维护 | 要兼容 MiuRead 与 KOReader 接口变化 | 不受 KOReader 更新影响，但要维护自己的运行时、设备和协议 |
| 启动、内存、续航 | 受宿主和插件实际实现影响 | 有优化空间，也可能更慢或更耗电；必须同设备实测 |
| 风险重点 | 插件/宿主版本组合、云端协议变化 | 排版质量、墨水屏刷新、休眠、退出恢复及云端协议变化 |

对本项目，优先评估新独立版能否作为基础。如果功能、设备兼容与源码条件合适，复用它比把成熟功能再实现一次更合理。现有 alpha 中的测试、账号隔离、入口和持久化模块按兼容性复用，不强行要求新软件采用 Go/Mesquite。

## 文件取得后的工作顺序

1. 记录文件名、版本、SHA-256、发布来源，辨认两份文件是不同版本、组件还是安装/更新包；先检查包内容和安装脚本。
2. 核实是否独立程序、系统 Web 应用、浏览器入口或其他运行方式；检查实际依赖、写入位置、源码及许可，不仅看“独立版”名称。
3. 建立可复现运行环境，逐项填写“已实现且验证、代码存在待验证、缺失、受限、未知”。没有源码时先做可完成的静态/运行检查，不假装可以可靠补齐所有复杂功能。
4. 对确认的缺失按阅读闭环、数据正确性和日常体验实施修复。用户已授权补功能，普通可逆开发不再重复请求批准；涉及确切未知业务意图或额外外部操作时再单独处理。
5. 同账号、同书、同章节与固定 Android 版本回归；原生入口、休眠和耗电由 KPW5 真机测试。起点、长佩开发目标继续保留。
